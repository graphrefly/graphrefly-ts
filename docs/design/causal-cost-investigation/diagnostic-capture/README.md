## 1. CPU 与经过时间的关系

下面是按条件、批次汇总的 block 中位数，每格16个 block。每个 block 有300个 measured 样本。

| 条件 | 批次（从0开始） | 构造 p95 中位数 ms | 构造时长总和中位数 ms | 共同跨度中位数 ms | 进程 CPU 中位数 ms |
|---|---:|---:|---:|---:|---:|
| BASE | 0 | 0.419 | 94.54 | 157.66 | 未观测 |

“共同跨度”是该 block 第一个 measured 样本 start 到最后一个 end；CPU 来自完整 block checkpoint，
还包括让出、内存读取、同步日志和清理，边界不相同。表中并列用于描述，不直接相减。
两个插桩条件共96个 measured block，其中95个的进程 CPU 大于 checkpoint elapsed 上界。
多线程进程 CPU 可超过墙钟经过时间；它不是负等待时间，也不是坏样本。

这些数据与“第一批存在更多执行活动”相容，不支持把变化简单解释成只有等待增多。
但它没有确定活动来自业务构造、记录/清理、VM 后台编译或其他进程内工作；
更不能把进程 CPU 全部归到 registry 或某个 graph 节点。

## 3. GC 观测能说明什么

CPU_GC 的48个 measured block 中，捕获 GC 事件与共同跨度重叠的并集总计 **288.27 ms**；
与记录的构造 start/end 窗口重叠总计 **0 ms**。这是 Node observer 捕获子集的区间关联结果，
不是“构造没有 GC”的证明。末端有限排空、后台活动以及未校准的 native GC/deopt 时钟边界保持。

因此不能把构造慢尾部直接归咎于这些已捕获事件，也不能删除相关 block 或扣掉 GC 后重新验收。
JIT、调度和构造独占 CPU 仍没有足够证据；本轮没有把推测写成根因。
