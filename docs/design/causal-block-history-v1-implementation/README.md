# 四格顺序诊断：第三批先测的一方较慢

本批完成固定 8 进程、19,200 样本（4,800 warmup / 14,400 measured），耗时 12.249763 秒；原业务 preflight 16 次 / 48 个计时外实例，零重试、零 not-run。独立 verifier 从全部样本重算逐批分位数、两半四格对比及交互比，结果一致。

**主要观察：第三批 8/8 次都是先测的一方较慢；翻转第三批顺序，较慢的一方也交换。**这在两种第二批历史和两次重复中一致。第一方/第二方 p95 比值为 1.116340–1.300899。

本轮将调查重点缩小到第三批的执行顺序及伴随的调用状态。不能继续把这组相同 reference 控制的差距解释为 Causal preset、registry 或架构 C 的业务实现成本；也不能宣称已经分离出纯位置成本、JIT 或 GC 根因。C/R 在本报告只表示测量槽位，两槽执行相同 reference 实现，与架构方案 C 无关。

## 四格与所有重复

固定加载 N→M0→M1、预检 M0→M1、C=M1/R=M0；两个业务 bundle、输入和原循环字节保持冻结，仅 driver 的 recipe 副本使用四格 orders。S00 也走相同副本路径。第一批固定 CR；进入第三批前，每槽已构造 800 次。

| 单元 | 三批顺序 | 第三批 C/R：前半 | 第三批 C/R：后半 |
| --- | --- | ---: | ---: |
| S00 | CR / RC / CR | 1.198240 | 1.116340 |
| S01 | CR / RC / RC | 0.827660 | 0.768699 |
| S10 | CR / CR / CR | 1.204385 | 1.208709 |
| S11 | CR / CR / RC | 0.831806 | 0.826768 |

CR 时 C 较慢；RC 时 R 较慢。两个预定重复均符合这一方向，没有删除任何不利数据。执行顺序为 S00,S01,S11,S10,S10,S11,S01,S00；前后半是顺序平衡的重复，不是共享状态的统计配对。

## 已预先规定的跨格对比

q 为各单元第三批 C/R。

| 半区 | q01/q00 | q11/q10 | q10/q00 | q11/q01 | 交互比 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 0 | 0.690730 | 0.690648 | 1.005129 | 1.005009 | 0.999881 |
| 1 | 0.688589 | 0.684009 | 1.082742 | 1.075542 | 0.993349 |

反转第三批时，C/R 在四组比较中均变为原来的 0.684009–0.690730。这个“约0.69”是相同实现的控制比值之比，不是 consumer 提速约31%。反转第二批的对比，在前半约1.005，后半约1.076–1.083；不能据此说前序历史没有影响。交互比接近1也不等于统计上证明无交互，本轮没有冻结这类阈值或显著性检验。

四格干预不能让不同进程共享相同 JIT/GC 状态。反转第三批同时改变 block 位置和调用点的先前状态；固定第一批和固定物理映射也限制推广。因此明确的是本轮顺序敏感性，不是底层单一机制。旧 native 事件时钟关联仍为 unknown，本次不重新作 GC/deopt 归因。

- 先检查 117,600 个历史 cold 样本的原始顺序与字段，再单独用旧 neutral verifier 重放其 28,800 样本。历史数据不混入本轮统计。
- 新 Python 最终 7 项测试 / 55 个负例通过；四个实际入口加载源派生 driver 和 stub factories，检查全部六 block 的构造/cleanup。JS 四格正例、18 个 AST 负例、23 个实际路径负例及一个双失败保留场景通过。
- 原 namespace RECIPE 由独立冻结常量在调用前后核对；实际冻结对象替身会拒绝写入。静态 AST 白名单另证明循环和 cleanup 原文保留、只有授权 guard/recipe 绑定变化。
