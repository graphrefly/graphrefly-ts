调查把问题推进了一步：**同位置配对之外，还有明显的按执行时间顺序聚集的耗时变化，且部分 block 的中位数也升高。** 单纯交换顺序或增加重复次数不足以解释它。现有证据尚不能分辨是主机调度、VM 执行状态、GC/编译活动，还是这些因素的组合。

## 完整数据呈现的差异

从已提交的归档读取并校验全部 635 个文件；重新核对 96,000 个样本，重算 240 个 measured block 的 p95 以及全部 20 对 q/g，均与原结果完全一致。每个 block 的统计使用原有 300 个 measured 样本，100 warmup 仍单独保留。

下表按实际进程编号分成前后两半，每半 20 进程、120 个 block。**这个分组及最大十分位检查是事后描述，不是新的验收、显著性检验、稳定区间或删样依据。**

| 描述量 | 前半：进程 0–19 | 后半：进程 20–39 |
|---|---:|---:|
| block p50 的中位数 | 0.292344 ms | 0.272375 ms |
| block p95 的中位数 | 0.413646 ms | 0.380312 ms |

全部 block 中，**p95 最大的 24 个全部来自前半段；p50 最大的 24 个也全部来自前半段**。这不是仅由 p95 的一个排序点造成的现象。各批、槽、进程的全部数值都在 [analysis.json](analysis.json)，没有只保留最差或最好的片段。

具体例子：进程 16（V），batch 0 第二槽的 p95 为 1.356083 ms，p50 为 0.415355 ms。将其 300 个 measured 样本按原顺序分成六个相邻的 50 样本窗口，中位数依次为 **0.439479、0.488521、0.560521、0.442708、0.291896、0.275792 ms**。同一 block 内前后也不一致；这六窗只是显示变化，不用于重算验收，也不表示后两窗是可选的“有效样本”。

控制对 1 的第一位置尤其直观：三批 p95 的同位置比值为 1.018778、0.404947、0.473370；用 p50 作纯描述时，相应比值仍为 0.981227、0.699736、0.722369。波动并非只存在于尾部。**这不构成改用 p50 的建议。**

## 不能通过去掉前半段解决

最后的控制对 19 仍失败：第一位置 g=0.875267。该位置三批 p95 比值分别为 0.867545、0.875267、0.939250；p50 描述性比值也分别为 0.942460、0.947924、0.941928。

因此，不能把前半段称为“主机预热”，删掉后宣布稳定；也不能据本次数据选择一个新的等待时长或 warmup 数。后半段还有未消除的配对差异。更不能把 1.356083 ms 或任何比值当作 registry 的新增成本：Z 的两槽都执行相同 reference。

## profile、内存和测量边界能说明什么

已核对实际 driver 的原始计时边界：每次先让出事件循环，读取 memoryBefore，再记录 start，构造 consumer，记录 end、memoryAfter，然后序列化并同步追加样本，最后 cleanup。`samples` 数组还保留样本记录到进程结束。源参考：`scripts/fixtures/spending-preset-performance-worker.ts:222` 的记录、`:240` 的让出、`:269` 的计时前内存读取及 `:329` 的清理；实际执行的派生源绑定在原归档中。

因此，`下一样本.start - 当前样本.end` 是可计算的同一进程时钟差，但包含记录、cleanup、下一次调度和内存读取等多项工作。上表显示这个**未计入构造窗口的间隔也变长**；不能把它全部算作磁盘 I/O、GC 或 scheduler 时间。同步记录和清理虽在计时窗口外，依然位于后续构造的执行历史中；本轮没有证明其中任何一项造成了差异。

内存/日志的证据也有明确边界：

- p95 最大的 24 个 block 中，有 21 个在全部 measured 样本的 before/after 间都未观察到 heapUsed 减少。它只排除“每次慢都伴随可见的净 heapUsed 下降”这种描述，**不能排除 GC**；分配可能抵消净变化，边界观测也不是事件时间线。
- 两半每进程 stdout 中 `[bailout ...]` 行数中位数都为 28；范围分别为 27–29 和 27–31。数量没有给出耗时、发生阶段或后台编译成本，不能据此宣布 JIT 无关。
- 原记录只有启动时一次 load average（4.1191 / 3.7852 / 3.7197），没有逐 block 的 CPU 执行时间、调度等待、频率或热状态。这个数字不能证明当时主机忙，也不能解释前后差异。
- GC/deopt native clocks 仍未校准。本轮不使用旧 uptime 偏移为慢样本标注 overlap / no-overlap，也不从别的进程借用校准。

**profile 仍有用，但此处需要先补足“时间花在哪类活动上”的证据。** Graph 节点 fn 的执行 profile 与整个 consumer 构造并非同一测量边界；逐节点构造计时也不能单独区分执行计算与被调度暂停。已有 profile 不能回答的部分不应靠新增更多节点标签来冒充解决。

## 下一步建议及取舍

推荐下一步先设计一个**固定工作量的诊断观测方案**，保持相同 reference/control 和业务边界，能区分每个 block 的实际 CPU 执行量与经过时间，并记录可对应阶段的 VM/系统证据。目标是回答“计算工作变多，还是相同工作经历了更多等待/干扰”，不是再次争取 Z 通过。

该设计至少应明确：

1. 观测位置和单位；构造、记录/清理、让出之间哪些时间可分、哪些不可分。CPU 总量不能伪装成节点独占 CPU 时间。
2. VM 事件到样本时钟的校准和失败时的 unknown；无法覆盖的后台活动继续显式留空。
3. 插桩本身的开销和状态影响如何与原计时路径区分；不默认“只在 block 边界”就没有干扰。
4. 固定数量、原样保留失败和无自动重试；不按观测结果动态挑稳定窗口、延长预热或过滤样本。

其他路线的取舍：继续调整配对公式暂时不能回答当前时间聚集现象；增加原样重复有成本且不消除未观测状态；直接禁用 JIT、强制 GC 或改成单次进程首构造会改变被测对象，只能先作为另行审阅的诊断干预，不能直接代替 consumer 性能资格。

这里尚未指定新的 flags、工具接口、采样次数或预算，所以**不是可启动的运行计划**。D169 不被悄悄替换，也不新增 D#、工作项、公共 API 或图内机制。可组合性、graph-owned lifecycle、退订不能结算义务以及分级隐藏目标保持；性能资格和人类/agent 易用性仍需各自证据。
