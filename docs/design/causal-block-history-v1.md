# 第三批顺序与前序历史：有限交叉诊断设计

2026-09-11 · 基线 `66d267a7` · 唯一 owner `graphrefly-ts`。
归属原 work `graphrefly-ts:CAUSAL-PRESET-ASSEMBLY-TS`；分类是私有诊断提案，
不是新的架构决定、实现授权或完成证据。本轮“继续”推进此设计及 commit，尚未实现或采样。
治理依据为 `graphrefly-ts:D168`（`decisions/execution.jsonl` 的 evaluation-method），
其正式方法、1.20/1.10 门槛及历史结果不变，不为一次诊断新增 D#。

推荐：**保持第一批不变，用四个单元分别反转第二批与第三批顺序。**
这能比较两个明确的顺序干预，但不保证一次定位 JIT、GC 或具体节点根因。
本页中的 C = candidate 槽，R = reference 槽；两槽运行相同 reference 业务实现，
与前面已选定的架构方案 C 无关。这里的 batch 是 benchmark 批次，也不是 graph wave/batch。

## 1. 已知事实与需要纠正的读法

[上一轮完整结果](causal-neutral-driver-v1-implementation/README.md)由 12 个进程、
28,800 个样本构成，独立 verifier 和异地解包重放一致；归档 188 个文件本轮再次逐字节
核对。第三批 C/R 比值全部 >1，范围 1.058498–1.371881，在中立 driver 和反转预检条件
中仍成立。它不要求本地/外部调用不对称，也不要求 C 最后预检。

但比值上升不能直接写成“C 本身都变慢”：对保留的 batch p95 作只读比较，C 第三批较
第二批上升为 10/12，R 第三批较第二批下降为 12/12。分母变化同样重要。这是描述性
复算，没有新增样本、显著性判定或原始收据改写。

原循环的六个 block 为：

```text
第一批       第二批       第三批
C → R   |   R → C   |   C → R
```

每 block 都是 100 warmup + 300 measured 次全新构造、记录、cleanup。第二批结束和第三批
开始连续使用 C；第三批 C 还同时具有“槽 C”“本批先运行”“上一 block 也是 C”的身份。
目前缺少反事实，不能把这三者拆开解释。

## 2. 四个单元和比较目标

所有单元仅使用中立 driver；固定 reference=M0、candidate=M1、加载 N→M0→M1、
预检 M0→M1，精确 `cold-P2-summary` / `control:true`。不继续扩展 hosted、module
角色和加载次序轴；过去的角色交叉足以支持优先改变顺序，但没有证明这些轴不存在交互。

| 单元 | 第一批 | 第二批 | 第三批 | 第三批开始前最后一槽 | 跨批边界重复同一槽 |
| --- | --- | --- | --- | --- | --- |
| S00 | C R | R C | C R | C | 是：C→C |
| S01 | C R | R C | R C | C | 否：C→R |
| S10 | C R | C R | C R | R | 否：R→C |
| S11 | C R | C R | R C | R | 是：R→R |

进入第三批前，四个单元都已构造 C 800 次、R 800 次；顺序不同，数量相同。
四种组合避免把“跨边界重复”始终绑定在同一槽；没有删除前两批、改变 warmup 数量，
或在采样时额外预热。

- S00↔S01、S10↔S11：固定前两批顺序，改变第三批谁先运行。
- S00↔S10、S01↔S11：固定第一和第三批顺序，改变第二批的历史。
- 比较两组顺序效应是否随另一轴变化，完整保留四格及各次重复。

**解释上限：**反转第三批不仅改变执行位置，也改变共同调用点进入各 block 时的状态；
反转第二批不仅改变最后一个槽，也改变第二批内的全部先后历史。前两批使用相同配置
不等于两个进程拥有相同 JIT/GC 状态。本设计识别的是顺序干预的差异，不是纯“位置成本”、
纯“立即前驱成本”或单一 VM 机制。第一批固定、物理映射固定仍是明确的剩余限制。

## 3. 实现边界与源码限定

现有 `scripts/derive-causal-neutral-driver.mjs:14` 的入口 guard、`:22` 的 RECIPE 绑定、
`:24` 的双 namespace factory、`:58` 的 AST body 派生是直接先例。
独立白名单在 `scripts/check-causal-neutral-source.mjs:21` / `:68`；没有公共 API 消费者。
本轮 Codegraph 核实了这两个私有文件及测试依赖，归档源核实了实际循环。

后续实现采用单独的 block-history 版本及输出目录；旧 neutral 工具、单次锁、归档和
verifier 的接受集合均保持原样。新版本继续从冻结原 worker 派生，沿用相同闭包、
makeArm、预检及 cleanup 结构。唯一新增的实验语义是四格 orders 白名单：

1. 在任何业务预检或 factory 调用前，入口和 driver 都校验精确 row、control、单元、
   reference/copy/preflight 映射、完整 orders；拒绝任意配置、额外 batch、同槽重复或漏槽。
2. 校验两份 namespace 的原始 RECIPE 与旧冻结值相同，再创建仅属于 driver 的浅副本，
   orders 来自四格常量。四格都经过相同构造路径，包括 S00。不写入 namespace RECIPE，
   不修改 worker 字节，不通过添加第三份业务 bundle 获得 driver。
3. 原 `runRow` 循环、每次 `setImmediate`、内存快照、计时、record、异常传播及 cleanup
   逐段保留原文，仍含受 cold guard 保护的非 cold 分支。只替换 guard 与 RECIPE 绑定；
   不把 orders 选择放入每个样本的计时区间，不缓存业务实例或改成逐样本交错。
4. worker metadata 记录实际有效 RECIPE；单独保留原始 RECIPE、单元和 orders digest，
   由独立 verifier 从固定四格重建预期。不能写“原 RECIPE 未变”掩盖诊断调度已改变。

S00 是**同轮新 driver 的基线**，不是旧 N0 的字节相同重跑。新的 recipe 绑定可能改变
driver 优化上下文；四格之间保持一致，旧 N0 只作历史背景，不合并数值或假设绝对耗时相等。
业务 bundle 仍绑定 SHA256 `d9d8606d73e1bcfad66097f027d63c99fc409571042c5f1e7efffaa645356fb2`，
输入、reference 资格与运行闭包继续按既有 archive_materials 资格校验。

## 4. 拟批准的单次预算与停止规则

固定进程序列：**S00,S01,S11,S10,S10,S11,S01,S00**。
前半和后半互为反序，每单元两次；先后半不是统计上的共享状态配对。

| 项目 | 上限 |
| --- | --- |
| 真实 consumer 采样进程 | 8 个，全新、串行 |
| 每进程 | 3 batches × 2 slots × (100 warmup + 300 measured) = 2,400 |
| 总样本 | 19,200：4,800 warmup、14,400 measured |
| 原业务 preflight | 每进程两次，共 16 次 / 48 个计时外实例 |
| 时间 | 每子进程 30 秒，从首个 spawn 起整轮 300 秒 |
| 自动重试 / 追加 | 0 / 0 |

Node v24.18.0 / V8 13.6.233.17-node.50、原 flags、输入保持冻结；环境选项与隐式 Node
注入仍拒绝，实际可执行文件和工具/parser 源码绑定。业务采样期间不并行测试或构建，
不新增 CPU/GC/node 插桩、强制 GC、冷却 sleep 或其它工作负载。

一次错误配置、预检失败、非零退出、超时、样本或结构错误就停，保留已耗用进程、全部
日志与剩余 not-run。工具失误也不返还名额；只能离线审阅保留材料。耗时比值较大或方向
反常本身不会中止其余预定单元；本诊断没有新的性能通过门槛，不“跑到明显”为止。
准备失败也保留 reservation 与失败记录；单次锁禁止清掉目录重跑。

## 5. 采样前的证明义务

沿用已有源码派生/实际加载/独立验证分工，不把现有工具的通过直接当作新 orders 已合格。

- **历史回归先行：**先核对现有四个归档共 117,600 个 cold 样本的原 2/3-arm 顺序、字段
  与已有分位数；本轮 neutral 28,800 单独重放。新四格验证不能回写或放宽旧 verifier。
- **静态独立检查：**新 generator 与独立 AST checker 分开实现白名单，绑定原函数、
  原/派生源、manifest 全字段及 parser 源码；检查声明不是 generator、没有额外业务定义。
  四格同源，只经显式 orders 数据改变；计时循环/cleanup 字节变化必须拒绝。
- **实际加载：**新入口四格都加载替身观察 imports、预检、完整六 block 的 factory
  module/slot/ordinal、record 和 cleanup。fake clock 跑实际派生循环，每次 factory
  仍位于 start/end 之间，constructionMs=0、preparationMs=0、ms=end-start。
  每 block 400 次、每槽每进程 1,200 次，前两批每槽 800 次，均由实际调用核验。
- **必须检测的真实变体：**声称翻转但实际固定旧 orders；只篡改 metadata；翻错批次；
  双重翻转抵消；漏槽/重复槽；少/多 batch；预先构造/缓存实例；漏 cleanup；错误 row、
  copy 自指、错误预检；修改 namespace 原 RECIPE。检验双失败保留、失败停止及单次锁。
- **独立统计/证据 verifier：**不能继续调用只接受 CR/RC/CR 的旧 verify_samples 来验证
  新顺序。新版本独立按四格生成全部坐标，核验 phase/segment/monotonic clocks、严格
  数量、每批每槽排序第 285 个 measured 值和原始三批中位数。拒绝第九个进程、错映射、
  错预检、缺完成、假时间跨度、摘要篡改及重新建立 digest index 后的上述错误。
- **完整原业务预检：**通过所有工具资格后，正式进程仍执行两份原 namespace preflight，
  比较 graph/reference/plain 后果；替身不构成业务等价证据。原 recipe 在运行前后均检查。
  前后检查不能单独证明没有瞬时写入，须结合静态无写入证据和实际冻结对象替身测试。

复用既有范围的离线资格与静态 QA；检查全部受影响私有工具及 lint/typecheck。全量 TS
仍需记录已有 D159 两项失败，不以刷新冻结 manifest“修绿”。无 public export 变动不增加
build 要求，禁止修 library/protocol 顺手消除测量问题。

## 6. 输出与预先约定的解释

保留每次重复、三批每槽绝对 p95（ms）、C/R、M1/M0、本批后运行/先运行，以及每槽
第三批/第二批比值。M1/M0 在本设计固定等于 C/R；明确其冗余，不声称独立身份验证。
按四格输出第三批比值 q00、q01、q10、q11，逐个前半/后半重复分别报告：

- 第三批反转对比：q01/q00、q11/q10。
- 第二批历史对比：q10/q00、q11/q01。
- 描述性交互比：(q11/q10)/(q01/q00)，不是显著性检验或根因判决。

在第三批 CR 时后/先=R/C；RC 时后/先=C/R。禁止统一把 C/R 标成后/先。
每个量均由原始样本重算；批间比较只描述进程内变化，不把三批当独立进程重复。
不按结果挑选一次重复、删除异常值、扣控制偏差或改用平均值替代冻结尾延迟规则。

| 观察 | 可以支持的后续方向 | 仍不能声称 |
| --- | --- | --- |
| 固定前序历史时，较慢槽随第三批先后移动 | 优先评估 block 顺序敏感性及更公平的调度方案 | 已获得纯位置成本；新正式方法已合格 |
| 第三批顺序不变，换第二批后差距稳定变化 | 前序顺序具有影响的候选证据 | 仅因最后一次调用或某个 JIT/GC 机制 |
| 两轴作用依赖另一轴 | 保留交互现象，进一步解释有价值 | 可简单相减分离成本 |
| S00 不复现或重复方向冲突 | 当前批次证据不足，审阅方法/环境，暂不选修复 | 删掉不利重复或追加至一致 |
| 四格仍固定同一物理槽较慢 | 本轮固定映射不足，角色/文件与其它因素仍待区分 | 已推翻上一轮观察或已证明 module 根因 |

`complete-diagnostic` 只表示执行/证据完整；性能资格继续 false。不预设“接近1”的新阈值，
不承诺八进程一定消除不确定。正式 D168 方法的改变仍是单独的方法审阅。

## 7. Q5–Q9

**Q5 — 层次与概念。**这是私有 benchmark 调度，不是 graph primitive、profiler API 或
用户配置。仅在已验证的中立 driver 绑定有限 orders；业务 consumer 仍由原 graph 运行。
普通用户、框架作者和维护者的 core/patterns/solutions 入口及分级隐藏目标不变。

**Q6 — 约束与维护。**INVARIANT：业务 bundle 无变化；每次构造、record、cleanup 一一
对应；原 recipe 不能被写入；采样不得由结果追加；源漂移即拒绝。长期风险是诊断工具
不断扩张，因此四格白名单只服务这次具体问题，旧工具保留回放，不建立通用调度框架。
固定第一批/物理映射和进程状态差异是接受的解释限制，不加一批未经批准的对照掩盖它们。

**Q7 — 简化与性能。**仅改变两批的 orders 数据，样本循环逐段保留。没有新的计时内探针、
额外 consumer 节点或 registry；library 增量运行成本为零（未改动）。工具端有有限的
计时外 recipe 副本和验证开销，不能断言它对 driver 优化毫无影响，所以保留同轮 S00。
R-node-thin / R-profile / R-dispatch-all / R-no-imperative 的 library 约束保持原样。

**Q8 — 备选。**

| 方案 | 形状 | 优点 | 代价与先例 |
| --- | --- | --- | --- |
| 全六 block 整体镜像 | CR/RC/CR 对 RC/CR/RC | 少单元；直接换槽位 | 前序与最终顺序同时变，无法分开；先例是已有 role crossover 的整组干预 |
